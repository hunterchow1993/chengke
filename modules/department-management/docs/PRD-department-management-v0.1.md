## 1. 文档目标

本文档定义部门树查询与维护、新增和编辑部门、层级移动、负责人设置、启停与删除保护、成员影响、权限生效、接口结构和验收标准，作为产品、设计、前端、后端和测试共同执行的需求基线。

部门管理主要回答以下问题：

1. 集团和部门如何形成一棵可维护的组织树。
2. 哪些管理员可以查看、创建、编辑或移动哪些组织节点。
3. 部门发生移动、停用或删除时，用户、角色授权和业务数据如何处理。
4. 组织变化如何及时影响数据权限、缓存和登录会话。

## 2. 背景与问题

用户管理已经依赖组织树定位人员，角色管理也依赖部门节点配置数据范围，但项目目前只有部门管理占位页面，缺少统一的组织维护规则。若直接进入开发，容易出现以下问题：

- 用户管理、角色管理分别维护一套部门数据，名称、状态和层级不一致。
- 普通管理员可以通过移动节点或修改父部门间接扩大自己的数据范围。
- 部门停用或删除后，已有成员、指定部门授权和业务数据归属失去有效引用。
- 组织变更后旧权限缓存继续生效，产生短时或长期越权。
- 大规模部门移动缺少影响预览、并发保护和可追溯审计。

因此，本模块必须成为租户内组织结构的唯一维护入口，其他模块只能消费组织数据或在授权范围内选择节点。

## 3. 产品目标

### 3.1 本期目标

- 让有权限的管理员快速查看、搜索和维护集团/部门树。
- 支持新增、编辑、同级排序和安全移动部门。
- 明确部门负责人、成员数、下级数和状态，降低组织维护成本。
- 防止通过组织调整绕过功能权限、数据权限和租户边界。
- 让用户管理、角色管理和业务数据查询共享同一套部门标识与层级关系。
- 对高影响操作提供影响摘要、二次确认、并发保护和审计记录。

### 3.2 非本期目标

- 不在部门管理中新增、编辑、停用用户或修改用户角色。
- 不在部门管理中配置功能权限、数据范围或敏感字段权限。
- 不包含员工入职、离职、调岗审批和业务数据交接流程。
- 不包含多租户之间的组织共享或跨租户部门移动。
- 不包含企业微信、飞书、钉钉或 HR 系统的组织同步。
- 不包含批量导入、批量导出和组织版本回滚。
- 不包含独立岗位、职级、汇报线和虚拟项目组模型。
- 不针对移动端单独设计，保证小屏基本可用即可。

## 4. 一期产品决策

| 决策项 | v1.0 结论 |
| --- | --- |
| 组织结构 | 每个租户维护一棵组织树 |
| 根节点 | 每个租户只有一个系统创建的集团根节点 |
| 节点类型 | 一期正式支持 `group`、`department`；`company` 作为后续候选 |
| 用户归属 | 一个用户必须直属一个可挂载用户的有效节点 |
| 部门负责人 | 每个部门最多一位负责人，可为空；负责人仍通过用户角色获得权限 |
| 部门编码 | 租户内唯一，创建后不可修改 |
| 同级名称 | 同一父节点下唯一，不同父节点可重名 |
| 层级深度 | 默认最多 10 层，最终上限待技术压测确认 |
| 排序 | 同一父节点内按 `sort` 升序、创建时间升序稳定排序 |
| 停用 | 停用部门不再接收新用户或新授权，但不自动停用已有用户 |
| 删除 | 仅无下级、无直属成员、无有效授权和无其他受保护引用的部门可软删除 |
| 移动 | 支持单节点连同全部后代移动；禁止移动到自身或后代节点 |
| 权限生效 | 组织变更后相关权限缓存立即失效；高风险变化按后端授权版本控制会话 |

## 5. 概念与数据边界

### 5.1 核心概念

| 概念 | 定义 |
| --- | --- |
| 组织节点 | 集团或部门在组织树中的统一抽象 |
| 集团根节点 | 当前租户组织树的唯一根，不允许删除、停用或移动 |
| 父节点 | 当前节点的直接上级组织 |
| 祖先节点 | 从根节点到当前节点父级路径上的全部节点 |
| 后代节点 | 当前节点下任意层级的全部子节点 |
| 直属成员 | `departmentId` 等于当前节点 ID 的用户，不包含下级部门用户 |
| 部门负责人 | 部门业务负责人标识，不等于系统管理员或数据权限角色 |
| 有效节点 | 状态正常且全部祖先节点均正常的节点 |

### 5.2 组织归属不等于权限

用户所属部门只表示人员的组织位置，不直接授予查看该部门或下级数据的能力。角色的数据范围才决定用户可以访问哪些数据：

- `self`：仅本人负责的数据。
- `department`：仅直属部门数据，不含下级。
- `department_and_descendants`：直属部门及全部授权后代。
- `selected_departments`：明确选择的部门及各自配置的下级范围。
- `all`：租户内全集团数据。

部门负责人也不因被选为负责人自动获得部门管理、用户管理或业务数据权限。需要的能力必须通过角色显式授予。

### 5.3 与其他模块的职责分工

| 场景 | 负责模块 |
| --- | --- |
| 新增、编辑、移动、启停和删除部门 | 部门管理 |
| 设置部门负责人 | 部门管理 |
| 查看某部门直属成员摘要 | 部门管理只读展示 |
| 新增用户、修改用户直属部门、停用用户 | 用户管理 |
| 配置角色的数据范围和指定部门 | 角色管理 |
| 调整线索、客户和商机负责人及归属 | 对应业务模块 |
| 查看组织变更日志 | 系统日志 |

部门详情可提供“查看成员”入口跳转到用户管理并带入部门筛选，但不得在部门页面内维护用户资料。

## 6. 目标用户与权限点

### 6.1 目标用户

| 用户类型 | 主要诉求 |
| --- | --- |
| 超级管理员 | 维护全集团组织结构，处理跨事业部调整和异常节点 |
| 系统管理员 | 在被授权范围内维护部门和负责人 |
| 部门管理员 | 查看本部门及授权下级，维护能力以角色权限为准 |
| 普通用户 | 默认不进入部门管理页面 |

### 6.2 权限编码建议

| 权限编码 | 权限说明 |
| --- | --- |
| `system:department:view` | 查看授权范围内的组织树和部门详情 |
| `system:department:create` | 在可管理父节点下新增部门 |
| `system:department:update` | 编辑部门名称、负责人、排序和备注 |
| `system:department:move` | 移动部门及其后代 |
| `system:department:status` | 启用或停用部门 |
| `system:department:delete` | 删除满足条件的部门 |
| `system:department:member:view` | 查看部门直属成员摘要并跳转用户列表 |

模块入口要求 `system:department:view`。前端按后端返回的节点级 `capabilities` 展示操作，接口必须重新校验权限，不得只依赖按钮隐藏。

## 7. 授权边界与防越权规则

### 7.1 可见范围与可管理范围

- 后端只返回操作者可见节点、定位这些节点所需的只读祖先路径和权限范围内的统计数据。
- 只读祖先仅用于理解路径，不代表可新增、编辑、移动、启停或删除。
- 新增部门时，父节点必须在操作者可创建范围内。
- 编辑、移动、启停和删除时，目标节点必须在操作者对应操作的可管理范围内。
- 负责人选择器只返回操作者有权查看且状态正常的用户；是否限制为本部门或其后代由第 22 节确认。
- 前端提交的 `parentId`、`leaderUserId`、节点 ID 和排序值都必须在服务端重新解析和校验。

### 7.2 移动的额外约束

- 禁止移动集团根节点。
- 禁止把节点移动到自身或任意后代节点，避免形成环。
- 新父节点必须正常、允许添加子部门且在操作者可管理范围内。
- 操作者必须同时有权管理被移动子树和目标父节点，不能用移动把不可管理节点带入自己的范围。
- 移动后树深度不得超过系统上限。
- 跨越权限边界或影响角色授权、成员可见范围时，必须展示服务端计算的影响摘要并二次确认。
- 服务端必须在事务内锁定或校验相关节点版本，防止并发移动形成错误路径。

### 7.3 保护规则

- 集团根节点不可移动、停用或删除，只允许超级管理员编辑有限展示信息。
- 当前操作者无权通过移动或停用使自己失去唯一管理路径；具体保护对象由后端能力标记决定。
- 唯一超级管理员所在节点的高风险变化必须被保护或要求先完成替代配置。
- 任何跨租户 ID 猜测统一拒绝，不泄露节点是否存在。

## 8. 信息架构与页面布局

```text
系统管理 / 部门管理
├── 组织树卡片
│   ├── 部门搜索
│   ├── 展开 / 收起 / 刷新
│   └── 集团与部门节点
└── 部门详情卡片
    ├── 部门摘要与状态
    ├── 基本信息
    ├── 直属成员与下级统计
    ├── 最近更新信息
    └── 新增下级、编辑、移动、启停、删除

新增 / 编辑部门 Drawer
移动部门 Dialog / Drawer
启停 / 删除确认 Dialog
```

页面采用“左树右详情”结构。组织树负责定位，右侧只展示一个选中节点的详情和操作，不再增加重复的部门表格。Header 面包屑是页面唯一定位信息，主体不重复展示“部门管理”大标题。

建议桌面宽屏左列 320px，右列 `minmax(0, 1fr)`，间距 16px。最终尺寸以独立 UI 设计文档为准。

## 9. 组织树查询与导航

### 9.1 首次进入

1. 管理员进入“系统管理 / 部门管理”。
2. 系统加载可见根路径、管理员所属节点及必要首层节点。
3. 恢复上次选择且仍有权限、仍存在的节点；否则选择管理员直属部门；再否则选择第一个可见节点。
4. 右侧加载选中节点详情和服务端计算的操作能力。
5. 任一请求失败时在对应区域展示错误和重试，不用空状态掩盖错误。

### 9.2 节点展示

每个树节点至少展示名称、类型图标、状态和必要统计：

| 内容 | 展示规则 |
| --- | --- |
| 名称 | 单行截断，Tooltip 展示完整路径 |
| 类型 | 集团与部门使用一致图标体系，不只依赖图标区分 |
| 状态 | 已停用节点显示文字状态和弱化样式 |
| 直属人数 | 只显示操作者有权查看的统计；无权限时不返回占位数字 |
| 展开箭头 | 只负责展开/收起，点击名称所在行负责选中 |
| 操作菜单 | 仅 Hover、Focus 或选中时出现，按 `capabilities` 渲染 |

### 9.3 搜索

- 搜索框占位提示为“搜索部门名称或编码”。
- 关键词最长 50 字符，首尾空格忽略，连续空格归一化。
- 搜索由服务端执行，不能要求前端加载整棵树后过滤。
- 搜索结果返回匹配节点及完整祖先路径；只读祖先仍不可操作。
- 命中文字高亮，清空后恢复搜索前的展开状态和选中节点。
- 无结果时显示“未找到相关部门”，并提供清空搜索操作。

### 9.4 懒加载与刷新

- 初始只加载必要节点，展开节点时按需请求直接子节点。
- 节点子级加载失败只影响当前节点，提供局部重试。
- 刷新保留搜索词、选中节点和展开状态；已删除或失权节点自动回退到最近可见祖先。
- 组织变更事件发生后，使相关树查询缓存失效，不能长期展示旧路径。

## 10. 部门详情

### 10.1 展示字段

| 字段 | 展示规则 |
| --- | --- |
| 部门名称 | 显示完整名称和状态标签 |
| 部门编码 | 等宽字体展示，可复制；集团根节点可使用系统编码 |
| 上级部门 | 显示直接父节点并可定位；根节点显示“—” |
| 部门负责人 | 显示头像、姓名和用户名；未设置显示“暂未设置” |
| 直属成员数 | 仅统计当前节点直属用户，不含下级 |
| 下级部门数 | 同时区分直接下级数和全部后代数 |
| 显示顺序 | 展示数值或排序摘要 |
| 备注 | 空值显示“—”，不占用过大区域 |
| 最近更新 | 更新时间和更新人 |

人数和下级数只能返回操作者有权获知的值。存在不可见成员或节点时，后端可返回 `hasHiddenReferences: true`，页面显示“存在不可见关联”，不能通过总数反推受限数据。

### 10.2 操作入口

| 操作 | 入口 | 说明 |
| --- | --- | --- |
| 新增下级 | 详情卡片主按钮 | 默认当前节点为父部门 |
| 编辑 | 常驻次按钮 | 打开编辑 Drawer |
| 移动 | 更多菜单 | 打开目标父部门选择器和影响预览 |
| 启用 / 停用 | 更多菜单 | 高风险确认后执行 |
| 删除 | 更多菜单末项 | 危险操作，满足删除条件时才可执行 |
| 查看成员 | 人数或链接 | 跳转用户管理并带入当前部门和“仅当前部门”范围 |

## 11. 新增部门

### 11.1 打开与默认值

1. 管理员在选中节点详情或树节点菜单点击“新增下级部门”。
2. 系统校验创建权限并获取可选父节点、负责人候选和字段约束。
3. 打开 560px 右侧 Drawer，标题为“新增部门”。
4. 默认父部门为触发入口对应节点，状态为正常，显示顺序为 `100`。

### 11.2 表单字段

| 序号 | 字段 | 提交值 | 必填 | 控件与规格 | 校验与说明 |
| ---: | --- | --- | --- | --- | --- |
| 1 | 部门名称 | `name` | 是 | 文本输入，40px 高 | 2–50 字符；同一父节点下唯一；去除首尾空格 |
| 2 | 部门编码 | `code` | 是 | 文本输入，40px 高 | 2–50 字符；租户内唯一；建议小写字母、数字和下划线；创建后不可改 |
| 3 | 上级部门 | `parentId` | 是 | 可搜索树形单选器 | 只能选择可创建下级且状态正常的节点 |
| 4 | 部门负责人 | `leaderUserId` | 否 | 可搜索用户单选器 | 仅返回可选用户；负责人不自动获得权限 |
| 5 | 显示顺序 | `sort` | 是 | 数字输入 | 整数 0–9999，默认 100，越小越靠前 |
| 6 | 状态 | `status` | 是 | 单选 / Switch | `active` 或 `disabled`；新增默认 `active` |
| 7 | 备注 | `remark` | 否 | 多行文本 | 最多 200 字符，显示剩余字数 |

负责人候选加载失败时不得用空列表替代真实结果后误保存；用户可以明确保持负责人为空。上级部门或负责人选择结果必须由后端重新校验。

### 11.3 保存流程

1. 点击“保存”后执行必填、格式、唯一性和父节点校验。
2. 前端校验失败时聚焦第一个错误字段。
3. 提交期间按钮进入 Loading 并阻止重复提交。
4. 后端在同一事务中创建节点、维护层级路径并写审计日志。
5. 创建成功后关闭 Drawer，刷新父节点子级并选中新部门。
6. 创建失败时保留输入，在字段或表单顶部展示稳定错误原因。

## 12. 编辑部门

- 编辑 Drawer 与新增共用字段和布局，部门编码只读并说明“创建后不可修改”。
- 集团根节点的父部门、编码和状态不可编辑；名称是否可编辑由超级管理员能力决定。
- 编辑详情必须包含 `version`；提交时携带版本号，冲突时禁止覆盖并提示重新加载。
- 修改负责人只改变部门负责人标识，不修改该用户的直属部门、角色或数据权限。
- 修改排序只影响同一父节点内的展示顺序，不改变层级和权限范围。
- 将正常部门直接编辑为停用不走普通保存，统一进入第 14 节停用流程。
- 存在未保存修改时关闭 Drawer，提示“放弃修改”或“继续编辑”。

## 13. 移动部门

### 13.1 操作流程

1. 管理员点击目标部门的“移动”。
2. 系统打开移动容器，展示当前完整路径和直属/下级摘要。
3. 目标父部门树只返回可移动到的有效节点，禁用当前节点及其后代。
4. 管理员选择目标父部门后，前端请求服务端影响预览。
5. 预览至少展示新路径、移动节点数、直属成员数、受影响角色授权数和权限范围变化提示。
6. 无影响或低风险移动可直接确认；跨权限边界或影响授权时要求二次确认。
7. 服务端重新计算影响并校验版本，不能信任前端预览结果。
8. 移动成功后刷新原父节点、目标父节点、被移动子树路径和相关详情。

### 13.2 层级与数据影响

| 对象 | 移动后的处理 |
| --- | --- |
| 部门及后代 | ID 保持不变，父关系和路径更新 |
| 直属用户 | `departmentId` 不变，组织路径随部门变化 |
| `department` 数据范围 | 仍指向用户当前直属部门，范围节点本身不变 |
| `department_and_descendants` | 根据新树重新计算后代集合，可能扩大或缩小 |
| `selected_departments` | 按稳定部门 ID 保留选择；包含下级时按新树重新计算 |
| `all` | 仍覆盖当前租户全部节点 |
| 业务数据归属字段 | 稳定部门 ID 不自动改写；可见范围根据新组织树重新计算 |

移动可能改变角色可见数据范围，因此必须清理涉及祖先、后代、成员和指定部门角色的权限缓存。若影响高风险权限，后端提升授权版本或撤销相关会话。

### 13.3 失败场景

- 目标父节点在确认前被停用、删除或移出授权范围：拒绝并要求重新选择。
- 节点被其他管理员修改：返回版本冲突，不覆盖最新结构。
- 移动后超过最大深度：拒绝并说明允许层级。
- 影响预览已过期：重新生成预览，不直接执行。
- 任一层级路径更新失败：整笔事务回滚，不能留下部分移动结果。

## 14. 启用与停用

### 14.1 停用规则

- 集团根节点不可停用。
- 停用父部门时，其全部后代在业务上视为不可用；一期建议要求管理员确认“同时停用全部正常后代”，不允许产生“父停用、子正常”的矛盾结构。
- 停用部门后不能新增下级、接收新用户、被用户调入、被设为新的角色指定部门或作为移动目标。
- 已有用户账号不自动停用，已有业务数据不自动转移。
- 已有角色对该部门的授权关系保留但暂不产生有效范围，页面显示“包含已停用部门”警告。
- 停用前展示直属成员、全部后代、相关角色和业务引用的影响摘要。
- 如果现有成员登录与业务处理会因此失去必要范围，是否强制先迁移由第 22 节确认。

### 14.2 启用规则

- 只有全部祖先均正常时才能启用部门。
- 若停用时级联停用了后代，启用父部门不默认自动启用全部后代，管理员需要明确选择，避免一次性恢复过大范围。
- 启用后可以重新接收用户和授权，但不会自动恢复已手动移除的角色配置。
- 启停成功后刷新树、详情、用户部门选择器和角色组织树缓存。

## 15. 删除部门

### 15.1 删除条件

部门同时满足以下条件时才允许软删除：

1. 不是集团根节点或其他系统保护节点。
2. 没有直接下级部门。
3. 没有直属用户，包括正常和停用账号。
4. 没有角色通过 `selected_departments` 直接引用。
5. 没有必须保留有效外键的业务数据、待处理审批或其他受保护引用。
6. 操作者拥有删除权限且仍在目标节点管理范围内。

是否要求部门先停用再删除列入第 22 节确认。无论结论如何，删除接口都必须按实际数据库状态重新校验，不能只依赖列表上的 `canDelete`。

### 15.2 删除交互

- 删除入口放在更多菜单末项，使用危险操作样式。
- 确认框展示部门名称和完整路径，并明确说明删除后不可用于新增用户或授权。
- 条件不满足时不展示空泛“删除失败”，应返回阻塞类型和可执行下一步，例如“请先移动 6 位直属成员”。
- 软删除后默认查询不再返回该节点，编码是否允许复用由第 22 节确认。
- 已有审计日志和历史业务记录仍保留原部门 ID 与必要名称快照。

## 16. 页面状态与反馈

| 状态 | 页面处理 |
| --- | --- |
| 首次加载 | 组织树和详情分别展示结构一致的 Skeleton |
| 无可见组织 | 树卡片提示“暂无可查看的组织”，详情区不发请求 |
| 未选择节点 | 详情区提示“请选择一个部门查看详情” |
| 搜索无结果 | 显示搜索摘要和“清空搜索” |
| 树加载失败 | 树区域显示原因和“重新加载组织” |
| 详情加载失败 | 详情区域保留当前选择并提供重试 |
| 无操作权限 | 允许只读查看，不渲染无权操作入口 |
| 并发冲突 | 提示数据已更新，提供重新加载，不覆盖新版本 |
| 节点失权或删除 | 自动选择最近可见祖先并说明当前节点已不可访问 |
| 高风险操作中 | 禁止重复提交，完成前不乐观修改组织树 |

Toast 只用于简短成功反馈。校验失败、权限拒绝、引用阻塞和网络错误必须在当前操作容器中保留可读信息。

## 17. 核心数据结构建议

### 17.1 组织节点

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | string | 租户内稳定唯一标识 |
| `tenantId` | string | 服务端从认证上下文取得，不接受前端授权输入 |
| `parentId` | string nullable | 根节点为空 |
| `name` | string | 节点名称 |
| `code` | string | 租户内唯一，创建后不可修改 |
| `type` | enum | `group` 或 `department` |
| `pathIds` | string[] 或等价结构 | 从根到当前节点的稳定 ID 路径 |
| `depth` | integer | 根节点建议为 0 |
| `leaderUserId` | string nullable | 部门负责人用户 ID |
| `sort` | integer | 同级显示顺序 |
| `status` | enum | `active` 或 `disabled` |
| `remark` | string nullable | 最多 200 字符 |
| `version` | integer | 乐观锁版本 |
| `createdAt` | datetime | 创建时间 |
| `updatedAt` | datetime | 最近更新时间 |
| `updatedBy` | string | 最近操作人摘要 |
| `capabilities` | object | 当前操作者对节点的服务端能力判断 |

层级存储可采用物化路径、闭包表或其他经过评审的方案。无论技术实现如何，都必须高效支持祖先、后代、环检测、子树移动和数据权限 SQL 过滤。

### 17.2 节点能力

```json
{
  "canView": true,
  "canCreateChild": true,
  "canEdit": true,
  "canMove": false,
  "canChangeStatus": true,
  "canDelete": false,
  "canViewMembers": true,
  "disabledReasons": {
    "move": "集团根节点不可移动",
    "delete": "存在直属成员"
  }
}
```

`capabilities` 只服务于前端展示和解释原因，不替代接口鉴权。执行操作时后端必须基于最新数据重新计算。

### 17.3 影响预览

```json
{
  "previewToken": "org_preview_20260809_001",
  "expiresAt": "2026-08-09T15:10:00+08:00",
  "affectedDepartmentCount": 4,
  "affectedDirectUserCount": 18,
  "affectedRoleCount": 3,
  "hasHiddenReferences": false,
  "riskLevel": "high",
  "messages": [
    "2 个角色的‘本部门及下级’范围将发生变化",
    "相关用户的权限缓存将在操作后失效"
  ]
}
```

预览令牌短时有效并绑定租户、操作者、目标节点、目标父节点和版本。执行接口必须重新校验，不允许把令牌当作跳过授权检查的凭证。

## 18. 后端接口能力建议

| 能力 | 方法与路径建议 | 关键说明 |
| --- | --- | --- |
| 加载组织根路径 | `GET /api/v1/system/departments/tree` | 返回可见节点、只读祖先和能力 |
| 加载直接子节点 | `GET /api/v1/system/departments/{id}/children` | 支持懒加载 |
| 搜索部门 | `GET /api/v1/system/departments/search` | 返回匹配节点和完整祖先路径 |
| 查询部门详情 | `GET /api/v1/system/departments/{id}` | 返回版本、统计、引用摘要和能力 |
| 查询可选父节点 | `GET /api/v1/system/departments/{id}/movable-parents` | 服务端排除自身、后代和无权节点 |
| 查询负责人候选 | `GET /api/v1/system/departments/leader-candidates` | 服务端分页、搜索和权限过滤 |
| 新增部门 | `POST /api/v1/system/departments` | 事务内维护路径和审计 |
| 编辑部门 | `PUT /api/v1/system/departments/{id}` | 携带 `version` 防并发覆盖 |
| 预览移动影响 | `POST /api/v1/system/departments/{id}/move-preview` | 返回短时预览令牌和影响摘要 |
| 移动部门 | `POST /api/v1/system/departments/{id}/move` | 原子更新整棵子树路径 |
| 预览状态影响 | `POST /api/v1/system/departments/{id}/status-preview` | 返回成员、后代和授权影响 |
| 修改状态 | `PATCH /api/v1/system/departments/{id}/status` | 处理级联规则、缓存和会话 |
| 删除部门 | `DELETE /api/v1/system/departments/{id}` | 按最新引用关系校验后软删除 |

接口路径以最终技术设计为准，但节点能力、可选范围和影响摘要必须由服务端计算。

## 19. 服务端校验顺序

1. 校验登录、账号状态、租户边界和 CSRF/请求完整性要求。
2. 校验对应功能权限。
3. 查询目标节点并校验版本、状态和节点级管理范围。
4. 校验父节点、负责人和其他关联对象属于同一租户且在可操作范围内。
5. 校验树结构：根保护、无环、最大深度、父节点有效性和同级唯一性。
6. 重新计算成员、角色授权、业务引用和权限影响。
7. 对高风险操作校验确认信息或有效预览令牌。
8. 在事务内写入节点、路径和必要关系变化。
9. 事务提交后使组织树、权限和相关业务查询缓存失效。
10. 写入成功或失败审计结果；需要时提升授权版本或撤销会话。

任一校验失败必须 fail closed，不得部分保存组织树变化。

## 20. 审计、安全与缓存

- 新增、编辑、负责人变更、移动、启停和删除都必须写系统日志。
- 日志至少记录租户、操作人、节点 ID、完整路径、操作类型、变更前后差异、影响摘要、时间、结果和失败原因。
- 移动操作应记录旧父节点、新父节点、旧路径、新路径和受影响节点数。
- 状态变化应记录是否级联、受影响后代数、成员数和角色授权数。
- 日志中的人员联系方式仍按敏感字段规则处理，不记录无关表单内容。
- 所有组织查询和写操作都必须包含租户条件，租户 ID 来自认证上下文。
- 组织变化后，使部门树、用户可选部门、角色可授权组织树和数据权限计算缓存失效。
- 对权限范围产生变化的移动和状态操作，更新相关用户授权版本；旧令牌不得长期保留旧范围。
- 缓存清理失败不能静默继续使用旧授权放行，应进入可观测的失败补偿或安全降级流程。

## 21. 非功能需求

### 21.1 性能与一致性

- 常规网络下，组织树首个可操作节点目标在 2 秒内展示。
- 树使用懒加载和服务端搜索，不一次性传输全集团全部节点。
- 常规节点展开、搜索和详情查询目标 P95 不超过 500ms，最终指标以真实数据压测为准。
- 单次移动子树超过 500 个节点时进入高风险提示；是否异步处理由技术评审决定。
- 组织写操作必须保证强一致的父子关系和路径，缓存采用提交后失效策略。
- 页面不对移动、停用和删除做乐观更新，必须等待服务端成功结果。

### 21.2 可访问性

- 组织树支持方向键导航、展开/收起、Enter 选择和可见焦点。
- Drawer、Dialog 和树形选择器打开后正确管理焦点，关闭后返回触发按钮。
- 状态、风险和只读祖先不能只用颜色表达。
- 图标按钮具有 Tooltip、`aria-label` 和至少 36×36px 桌面点击热区。
- 表单使用常驻 Label，Placeholder 不替代字段名称。

### 21.3 响应式与兼容性

- 优先支持最近两个主要版本的 Chrome 和 Edge。
- 设计基准宽度为 1440px。
- 内容宽度 ≥1200px 使用左树右详情。
- 1024–1199px 可缩窄组织树并保持详情可用。
- <1024px 组织树通过 Drawer 打开，选择节点后返回详情；编辑 Drawer 占满可用宽度。
- 任何宽度不得出现页面级横向溢出或无法触达确认按钮。

## 22. 待确认项

以下事项会影响最终范围、交互或接口设计，需要在开发前完成业务评审：

1. 一期是否需要正式支持 `company` 子公司节点；如支持，是否限制公司只能挂在集团下。
2. 部门负责人是否必须是本部门直属成员，还是允许选择上级或下级部门用户。
3. 同一用户能否同时负责多个部门。
4. 部门编码的生成方式、正则和软删除后是否允许复用。
5. 最大组织深度是否固定为 10 层，是否需要按租户配置。
6. 停用父部门是否必须级联停用全部后代，还是允许保留子节点状态但计算为不可用。
7. 停用有成员的部门前，是否必须先迁移成员或停用账号。
8. 删除部门是否要求先停用，以及哪些历史业务引用会阻止删除。
9. 部门移动后，历史线索、客户和商机的 `ownerDepartmentId` 保持原值还是随负责人当前部门更新。
10. 跨事业部移动是否需要审批，还是仅超级管理员二次确认即可。
11. 大规模移动是否需要异步任务、进度展示和失败回滚报告。
12. 普通部门管理员是否可以编辑本部门本身，还是只能管理下级部门。
13. 直属人数、后代人数和受影响角色数在存在部分不可见对象时如何展示文案。
14. 是否需要拖拽排序和拖拽移动；一期建议仅使用明确表单操作，降低误操作和无障碍成本。
15. 是否接入第三方通讯录；若后续接入，需要定义本地字段与外部字段的权威来源和冲突策略。

## 23. 验收标准

### 23.1 组织树与详情

- [ ] 页面只返回操作者可见节点及必要只读祖先，不泄露其他组织结构和人数。
- [ ] 首次进入、恢复选择、展开、搜索、清空搜索和刷新行为符合本文档。
- [ ] 搜索由服务端执行并返回完整祖先路径，不依赖前端全量树。
- [ ] 组织树和详情的加载、空、失败、无权限和节点失效状态都有明确反馈。
- [ ] 直属成员数不包含下级部门成员，受限统计不会泄露不可见总数。
- [ ] 查看成员正确跳转用户管理并带入当前部门与“仅当前部门”范围。

### 23.2 新增与编辑

- [ ] 部门名称、编码、父部门、负责人、排序、状态和备注的校验符合本文档。
- [ ] 部门编码租户内唯一且创建后不可修改，同级名称唯一。
- [ ] 无权父节点和负责人不能通过伪造请求提交。
- [ ] 集团根节点的父级、状态、移动和删除入口受到保护。
- [ ] 编辑并发冲突不会覆盖其他管理员的最新修改。
- [ ] 未保存表单关闭时有明确确认，失败后保留已填写内容。

### 23.3 移动、启停与删除

- [ ] 部门不能移动到自身或后代，移动后不能超过最大深度。
- [ ] 移动原子更新整棵子树路径，失败不会留下部分结果。
- [ ] 跨权限边界或影响授权时展示服务端影响预览和二次确认。
- [ ] 部门移动后相关用户、角色和业务查询使用新组织范围，旧缓存及时失效。
- [ ] 停用节点不能接收新用户、授权、下级部门或作为移动目标。
- [ ] 只有祖先正常的部门才能启用。
- [ ] 有下级、成员、角色引用或受保护业务引用的部门不能删除，并返回可执行的阻塞原因。
- [ ] 删除为软删除，历史日志和必要业务记录保持可追溯。

### 23.4 权限、安全与审计

- [ ] 页面入口、按钮、节点数据和接口分别执行功能权限与数据范围校验。
- [ ] 组织归属和负责人身份不会自动授予部门或业务权限。
- [ ] 普通管理员不能通过新建、移动、停用或删除扩大自身管理范围。
- [ ] 跨租户节点、用户和角色 ID 请求全部被拒绝。
- [ ] 组织变化后相关权限缓存、授权版本和必要会话按规则更新。
- [ ] 新增、编辑、负责人变更、移动、启停和删除均生成完整审计记录。

### 23.5 界面一致性

- [ ] 产品名称统一为“澄客 CRM”，路由与侧栏名称统一为“部门管理”。
- [ ] 页面符合全局卡片、颜色、字体、圆角、图标和按钮规范。
- [ ] `Building2` 用于部门管理语义，通用操作使用设计系统白名单图标。
- [ ] Header 已有面包屑时，正文不重复同名页面标题。
- [ ] 高风险操作收纳在更多菜单并使用确认流程，不长期占据主视觉。
- [ ] 键盘可以完成树导航、表单填写和确认操作，状态不只依赖颜色。
