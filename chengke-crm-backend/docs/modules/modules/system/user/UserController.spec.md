## 1. 功能目标

### 1.1 业务问题

澄客 CRM 需要为后台账号提供统一的用户管理能力（PRD §1、§3.1）：

- 让有权限的管理员在组织范围约束下查询、创建、编辑、启用、停用系统用户，并为忘记密码的用户重置密码。
- 让用户身份、部门、角色、状态和联系方式在一个页面内清晰呈现。
- 为角色权限、部门管理和审计日志模块提供稳定的用户基础数据。

### 1.2 使用方

| 使用方 | 说明 |
| --- | --- |
| 超级管理员 | 管理全部账号、角色和状态（PRD §4.1，已确认） |
| 系统管理员 | 在授权范围内新增、编辑和停用用户（PRD §4.1，已确认） |
| 部门管理员 | 查看并维护本部门成员，具体权限 **待确认**（PRD §4.1） |
| 普通用户 | 默认不进入用户管理页面（PRD §4.1，已确认）；个人资料自助维护范围 **待确认** |
| 角色管理模块（后端消费方） | 角色成员调整时会改写用户的角色（角色管理 PRD §4.3，已确认） |
| 登录模块（后端消费方） | 登录时消费账号状态与 `forcePasswordChange`（登录 PRD §8，已确认） |

### 1.3 期望结果

- 用户数据的查询、创建、编辑、启停、重置密码全部受功能权限 + 数据范围 + 敏感字段权限三层约束。
- 越权访问不暴露资源存在性（范围外统一按「不存在」处理，见 §5.2 与 §18 P0-5）。
- 并发编辑不互相覆盖（版本冲突检测）。
- 用户创建 / 调岗与部门引用登记保持一致，部门删除不会被遗留用户引用悄悄绕过。
- 所有高风险操作可审计追溯。

## 2. 功能范围

### 2.1 本次包含

- 分页查询用户列表（组织节点 + 是否包含下级 + 关键词 + 状态筛选）。
- 查询用户详情（编辑抽屉回填）。
- 新增用户（含初始密码、首次登录改密开关）。
- 编辑用户资料（用户名只读；密码不在编辑接口变更）。
- 启用 / 停用单个用户；批量停用用户（逐项校验、允许部分成功）。
- 重置用户密码。
- 用户名、手机号可用性校验（表单失焦异步校验）。
- 用户管理页组织树（可见节点、懒加载、搜索、权限范围内用户数）。
- 新增 / 编辑表单的可选部门与可选角色选项。
- 手机号、邮箱等敏感字段的脱敏返回。
- 用户操作审计日志。
- 用户与部门之间的跨模块引用登记（对接部门模块已有的引用登记机制）。

### 2.2 本次不包含

- 删除用户（PRD §7.6、§15-11：是否保留、软删除还是物理删除 **待确认**；PRD §16 v1.0 范围未包含删除）。
- 导出用户（`system:user:export` 非本期能力，PRD §4.2，已确认）。
- 批量导入用户（PRD §16 后续版本）。
- 部门、角色的创建与编辑逻辑（PRD §3.2，已确认）。
- 角色权限、数据权限、敏感字段权限的配置（由角色管理模块负责，PRD §3.2，已确认）。
- 员工入职、离职审批流程；线索 / 客户 / 商机负责人转移流程（PRD §3.2，已确认）。
- 单点登录、企业微信 / 飞书 / 钉钉同步、移动端界面（PRD §3.2，已确认）。
- 用户登录、Token 签发与刷新、会话管理（由认证 / 登录模块负责；认证 Spec §1 已确认边界）。
- 多角色、用户级权限例外（PRD §4.7：v1.0 单角色，已确认）。
- 个人资料自助维护页面（普通用户场景，**待确认**）。

## 3. 业务对象

| 业务对象 | 说明 | 关键字段 | 与其他对象关系 |
| --- | --- | --- | --- |
| 用户 | 系统登录账号与人员资料 | id、username、name、mobile、status、forcePasswordChange | 归属一个部门；v1.0 拥有一个角色（已确认，PRD §4.7） |
| 部门（组织节点） | 组织树节点，用户管理引用不维护 | id、parentId、name、nodeType、status、path | 一个部门下有多个用户；由部门管理模块维护（已存在） |
| 角色 | 权限载体，用户管理引用不维护 | id、name、status、builtIn、权限集合 | 一个角色可被多个用户使用；由角色管理模块维护（**未实现**，见 §18 P0-2） |
| 用户审计日志 | 用户操作的审计记录 | 操作人、目标用户、操作类型、时间、结果 | 多对一 用户 |
| 部门引用 | 用户对部门的跨模块引用登记 | reference_type、reference_key、protected | 多对一 部门；阻止部门被删除（已存在，见 §17） |
| 操作者上下文 | 单次已认证请求的操作者快照 | tenantId、actorId、permissions、manageableDepartmentIds、manageAllDepartments | 来源于 JWT（认证 Spec §2.3，已确认） |

依赖关系：

- 用户 **依赖** 部门（必填 `departmentId`，部门必须先存在且可用）。
- 用户 **依赖** 角色（必填 `roleId`，角色数据源尚未实现，**待确认**，见 §18 P0-2）。
- 用户 **被依赖**：登录模块读取账号状态 / 密码 / `forcePasswordChange`；角色管理模块可改写用户的角色；业务模块（线索 / 客户 / 商机）将以用户作为负责人（PRD §4.4，后续模块）。

### 4.2 全局约定

**认证与操作者上下文（已确认，沿用认证 Spec）**

- Bearer JWT；`tenantId`、`actorId`、功能权限、可管理部门范围（`manageableDepartmentIds`、`manageAllDepartments`）从认证上下文解析。
- 请求体 / 参数一律不接受 `tenantId` 与操作者字段。

**统一响应外壳 `ApiResponse<T>`（已确认，全局既有实现）**

| 字段 | 类型 | 一定存在 | 业务含义 |
| --- | --- | --- | --- |
| `code` | String | 是 | 业务码；成功为 `OK` |
| `message` | String | 是 | 展示消息 |
| `data` | T | 成功时 | 业务数据 |
| `requestId` | String | 是 | 请求追踪 ID |
| `timestamp` | OffsetDateTime | 是 | 响应时间 |

**分页外壳 `PageVO<T>`（已确认，全局既有实现）**

| 字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `items` | Array | 当前页数据 |
| `page` | int | 页码 |
| `pageSize` | int | 每页大小 |
| `total` | long | 总条数；仅统计当前数据权限范围内的结果，不能泄露全集团用户数量（PRD §4.9 已确认） |

**共享枚举**

| 枚举 | 取值 | 说明 | 状态 |
| --- | --- | --- | --- |
| 用户状态 `status` | `active`（正常）/ `disabled`（已停用） | 前后端共享稳定编码，不提交中文值 | 已确认（PRD §8.4.1） |
| 状态筛选「全部」 | 不传 `status` 参数 | **禁止**传 `all` | 已确认（PRD §8.4.1） |
| 组织节点类型 `nodeType` | `group` / `department` | 沿用部门模型 | 已确认（部门 Spec） |
| 是否强制改密 `forcePasswordChange` | `true` / `false` | 仅创建或重置密码时设置 | 已确认（PRD §8.3） |

**通用参数约定**

- ID 均为 UUID；时间为 `OffsetDateTime`，前端按 `YYYY-MM-DD HH:mm:ss` 展示（PRD §7.5）。
- 关键词类参数 ≤50 字符，首尾空格去除后为空按空处理。
- 分页参数：`page` ≥1 默认 1；`pageSize` 1–100 默认 10（默认 10 已确认，PRD PAGE-02；上限 100 为设计建议，对齐部门模块）。

**通用错误行为**

- 功能权限在 HTTP 层与业务层各校验一次（双层校验，部门 Spec §17.3 已确认的项目约定）。
- 数据范围外 / 不存在的目标统一返回 404「不存在」，不暴露存在性（见 §5.2）。
- 错误码唯一注册表见 §11.2；API Spec 只能引用该表中的错误码。
- 领域异常（422）统一消息：「用户操作不符合业务规则」（设计建议，对齐部门模块约定）；保护账号场景使用专用消息（见 §5.3）。

### 4.3 关键设计决策（设计建议，需评审）

| 决策点 | PRD 原文 | 本 Spec 决策 | 理由 |
| --- | --- | --- | --- |
| 编辑接口形态 | 「编辑提交只发送发生变化的字段，具体采用 PATCH 或完整更新由接口设计决定」（PRD §8.6） | PUT + 完整字段 + `version` | 与部门模块编辑接口一致，避免两种更新语义并存 |
| 编辑并发策略 | 「具体并发策略待技术评审」（PRD §6.3） | 版本号乐观锁冲突检测 | 与部门模块一致（部门 Spec §19） |
| 组织树接口归属 | 页面需要组织树 + 人数（PRD §7.2） | 用户管理自建组织树接口（#10–#12），不直接复用部门管理树接口 | 权限点不同（`system:user:view` vs `system:department:view`）；人数口径不同（权限范围内子树用户数 vs 部门直属成员数） |

## 5. 共享业务规则与决策表

> 本章只收录影响多个 API 的规则；单个 API 特有的规则写在该 API 的 Spec 内。

### 5.1 可见范围（读）

**触发** → 持有 `system:user:view` 调用列表 / 详情 / 组织树。

**判断**
- 全量范围操作者（`manageAllDepartments=true`）→ 可见租户内全部未删除部门的用户。
- 范围操作者 → 用户可见 ⇔ 用户所属部门 ∈ 操作者可管理部门集合。
- 可见部门集合 = 可管理部门 ∪ 其祖先（祖先仅用于定位，祖先节点直属用户不在可管理集合内则不返回）。

**行为** → 仅返回范围内用户；总数只统计范围内结果（PRD §4.9）；范围外目标按 §5.2 处理。

消费方：user-list、user-detail、user-org-tree、user-org-tree-children、user-org-tree-search。

### 5.2 越权与存在性保护

**触发** → 任何以用户 / 部门 / 角色 ID 为目标的请求。

**判断** → 目标不存在，或存在但不在操作者范围内。

**行为** → 统一返回 404「不存在」语义，不区分两种情况（沿用认证 Spec §3.4 / 部门 Spec §9.1 约定）。

> 差异记录：PRD §4.9 编辑场景描述为「返回无权限」；本 Spec 按项目既有约定采用 404，编辑保存时目标已移出范围的消息使用 PRD 指定的「该用户已不在你的管理范围内」。该口径差异列入 §18 P0-5。

### 5.3 保护账号规则

| 保护对象 | 规则 | 来源 |
| --- | --- | --- |
| 当前登录用户本人 | 不允许把本人状态改为 `disabled`；不允许修改本人角色（本人角色 / 数据范围 / 账号状态不可自改） | 已确认（PRD §4.8、§8.3） |
| 系统唯一超级管理员 | 不允许改为 `disabled` | 已确认（PRD §7.6、§8.3） |
| 持有未转移业务数据的用户 | 能否停用 **待确认**（§18 P1-7） | PRD §7.6 |

- 「唯一超级管理员」= 持有超级管理员内置角色的最后一名正常状态用户；超级管理员内置角色（`super_admin`）的识别机制依赖角色管理模块（§18 P0-2）。
- 违反保护规则的错误码：`USER_SELF_DISABLE_FORBIDDEN`（本人）、`USER_LAST_SUPER_ADMIN_PROTECTED`（唯一超级管理员）、`USER_SELF_ROLE_CHANGE_FORBIDDEN`（本人角色），见 §11.2；保护规则的检查必须以提交时的最新数据判断（见 §10 并发）。

**保护账号决策表（供 user-update / user-status / user-batch-disable 消费）**

| 目标是本人 | 目标是唯一超级管理员 | 允许停用（改为 `disabled`） | 系统行为 |
| --- | --- | --- | --- |
| 是 | — | 否 | 拒绝，消息「不能停用自己」 |
| 否 | 是 | 否 | 拒绝，消息「唯一超级管理员受保护」 |
| 否 | 否 | 是 | 继续状态变更流程 |
| 否 | 超管但非唯一 | **待确认**（§18 P1-11） | — |

### 5.4 授权边界（防越权，已确认，PRD §4.8）

- 管理员只能创建或编辑自己数据范围内的用户。
- 管理员不能给他人分配自己不拥有的功能权限或更大的数据范围（角色授予校验机制 **待确认**，§18 P0-8）。
- 管理员不能把用户移动到自己无权管理的部门。
- 不允许通过批量操作绕过单条权限校验（批量逐项校验）。
- 部门移动、角色变更和用户调岗后，权限缓存必须立即或在极短时间内失效（见 §9 提交后一致性）。
- 前端隐藏按钮不替代服务端校验（后端必须再次验证，PRD §11）。

### 5.5 唯一性规则

| 字段 | 范围 | 规则 | 来源 |
| --- | --- | --- | --- |
| `username` | 租户内 | 忽略大小写唯一；创建后不可修改 | 已确认（PRD §8.2） |
| `mobile` | 租户内 | 唯一；编辑时排除本人 | 已确认（PRD §8.2 / §8.3） |
| `email` | — | PRD 未要求唯一，不设唯一约束 | 已确认（不额外增加规则） |

最终一致性由数据库唯一约束兜底；并发冲突时后提交者收到重复错误（见 §10）。消费方：user-create、user-update、两个可用性校验接口。

### 5.6 敏感字段脱敏

| 字段 | 完整查看权限 | 未授权行为 | 来源 |
| --- | --- | --- | --- |
| 手机号 | `system:user:mobile:full` | 返回 `138****8006` 格式（前 3 位 + `****` + 后 4 位） | 已确认（用户管理 PRD §4.3、角色管理 PRD §13.1） |
| 邮箱 | `system:user:email:full` | 返回部分脱敏邮箱（具体格式 **待确认**，§18 P1-1） | 脱敏要求已确认（角色管理 PRD §13.1） |

- 脱敏由服务端在返回前完成；完整值不得先返回再由前端遮挡（角色管理 PRD §5.2 已确认）。
- 列表、详情、（未来的导出）使用相同字段权限（角色管理 PRD §13.2）。

消费方：user-list、user-detail。

### 5.7 部门引用登记（跨模块）

**触发** → 用户创建 / 换部门 / （未来的删除）。

**行为**（对接部门模块既有引用登记机制，V1 迁移说明确认该机制面向用户模块）
- 创建用户：为所属部门登记 `reference_type='user'`、`protected=true` 的引用。
- 换部门：注销旧部门引用并登记新部门引用。
- 效果：存在用户的部门不能被软删除（部门 Spec §10.3 已确认删除阻塞）。

消费方：user-create、user-update。

## 6. 状态流转

用户状态机（`status`：`active` / `disabled`）：

```text
（创建）──→ active ←──启用──→ disabled
```

| 当前状态 | 操作 / 条件 | 新状态 | 是否允许 | 业务说明 |
| --- | --- | --- | --- | --- |
| —（新建） | 新增，默认 | `active` | 是 | 默认正常（已确认） |
| —（新建） | 新增，显式 `disabled` | `disabled` | 是 | 允许创建停用账号（PRD §8.2 已确认） |
| `active` | 停用；通过保护账号决策表（§5.3） | `disabled` | 是 | 不可登录；历史业务数据保留（已确认） |
| `active` | 停用；保护账号 | — | 否 | 422 保护规则 |
| `disabled` | 启用 | `active` | 是 | 二次确认后恢复（PRD §6.5 已确认） |
| 任意 | 重复变更为相同状态 | 不变 | **待确认** | user-status.spec.md §12 |

- 初始状态：`active`（默认）或 `disabled`（显式创建）。
- 中间状态：无。
- 终态：无（v1.0 无删除能力）。
- 状态消费方：登录模块依据 `status` 决定是否允许登录（登录 PRD 已确认），用户管理模块不负责会话拦截。

| --- | --- | --- |
| 全量范围（`manageAllDepartments=true`） | 租户内全部用户 | 全部用户 |

| 范围外目标 | 404（不暴露存在性） | 404（不暴露存在性） |

- v1.0 范围来源：JWT `manageable_department_ids` 与 `system:department:manage:all`（认证 Spec 已确认的现有机制；用户管理复用该机制为**设计建议**）。

1. 认证边界：JWT 有效性与账号状态。
2. HTTP 层功能权限表达式校验。
3. 业务层二次功能权限校验 + 数据范围校验。
4. 返回前敏感字段处理（§5.6）。

授权边界（防越权）规则见 §5.4。

## 9. 事务与数据一致性

单个接口内部的原子性要求写在该接口的 API Spec 第 10 节；本章只写全局（跨接口、系统级）要求。

### 9.1 提交后一致性（跨存储，非同一数据库事务）

| 触发 | 必须发生 | 来源 |
| --- | --- | --- |
| 用户的部门 / 角色 / 状态变化、重置密码 | 租户授权版本递增，使旧授权缓存 / 令牌范围按既有机制失效 | 已确认要求（用户管理 PRD §4.8「权限缓存必须立即失效」；递增授权版本为部门模块已确认的既有机制） |
| 用户创建 / 换部门 / 启停 | 部门树相关缓存失效（部门树的直属成员数会因用户变化而过期） | 设计建议（部门 Spec §24 仅在部门写后清缓存，未覆盖用户写） |

> 已知缺口：认证模块当前代码尚未比对 JWT `permission_version` 与 Redis 租户授权版本。目标规则已确认（认证 Spec §7.3、登录总览 §5.6：下一次业务请求 HTTP 409 `PERMISSION_VERSION_CHANGED`）。在实现补齐前，权限失效可能仍滞后于 Token 有效期。

### 9.2 回滚要求

任何写操作在其一致性组内任一步失败 → 该组全部不生效；不允许部分成功的中间数据进入数据库。

### 9.3 批量操作的部分成功语义

批量停用中「部分成功」指**用户之间**相互独立：单个用户的「状态 + 审计」仍必须原子，单个用户失败不得回滚其他用户（已确认要求，PRD §4.9）。

## 10. 并发与幂等

### 10.1 并发风险与必须保证的结果

| 场景 | 可能问题 | 系统必须保证 |
| --- | --- | --- |
| 两个管理员同时编辑同一用户 | 后提交覆盖先提交 | 后提交者收到版本冲突（409），先提交数据保留（已确认需求：提示刷新后重试，PRD §6.3；机制为乐观锁版本，设计建议） |
| 并发创建相同用户名 / 手机号 | 重复数据 | 唯一约束兜底，仅一个成功，另一个返回重复错误 |
| 编辑与状态变更并发（不同字段） | — | 均为行内更新，以提交顺序为准；状态变更的保护规则必须基于提交时最新状态判断（读取与更新须串行化到同一行） |
| 停用与启用并发作用于同一用户 | 状态抖动 | 最终状态为后提交者的合法变更；保护账号（本人 / 唯一超级管理员）在任何交错下都不得被停用 |
| 「唯一超级管理员」判定并发（同时停用两个超管之一） | 判定各自看到「还有另一个」导致双停用 | 判定与更新必须对同一行串行化，最终至多允许一个成功，不得出现零个正常超管的结果 |
| 批量停用与单条操作并发 | 逐项结果与最终状态不一致 | 逐项以提交时最新状态判断；结果如实反映每项执行结果 |

不指定具体锁实现（数据库行锁 / 分布式锁等由实现阶段按项目约束选择；`version` 冲突检测为本 Spec 定义的契约行为）。

### 10.2 幂等与重复提交

| 接口 | 重复提交行为 |
| --- | --- |
| 新增用户 | 相同用户名 / 手机号的重复请求返回重复错误（唯一性兜底）；不引入额外幂等令牌（PRD 未要求） |
| 编辑用户 | 相同 `version` 的重复请求：第一个成功后续返回版本冲突 |
| 单个状态变更 | 重复同态变更的处理 **待确认**（user-status.spec.md §12） |
| 批量停用 | 重复请求中对已停用用户的处理 **待确认**（user-batch-disable.spec.md §12） |
| 重置密码 | 每次请求都产生新凭据与审计，不做幂等去重（是否限制频率 **待确认**，user-reset-password.spec.md §12） |
| 可用性校验 / 组织树 / 选项 | 只读，可安全重试 |

## 11. 异常处理与错误码

### 11.1 异常处理约定

| 异常类别 | 系统行为 | HTTP |
| --- | --- | --- |
| 参数异常（缺失 / 格式 / 长度 / 枚举非法） | 拒绝请求，不读业务数据 | 400 |
| 权限异常（无功能权限） | 拒绝 | 403 |
| 数据异常 / 越权（不存在或范围外） | 拒绝，不暴露存在性（§5.2） | 404 |
| 冲突异常（唯一性、版本） | 拒绝，数据不变 | 409 |
| 业务 / 状态异常（领域规则、保护账号、目标状态不允许） | 拒绝；422 统一消息「用户操作不符合业务规则」，保护场景用专用消息 | 422 |
| 系统异常（未映射数据库错误） | 整笔回滚（批量中单项失败） | 500 |
| 认证异常 | 按认证 Spec：`AUTHENTICATION_REQUIRED` / `AUTHENTICATION_INVALID` | 401 |

各接口特有的异常场景与错误码映射写在该 API Spec 的第 9 节。批量接口逐项失败不改变整体 HTTP 状态（200 + 逐项结果）。

### 11.2 错误码总表（唯一注册表）

| 错误码 | 场景 | 含义 | HTTP |
| --- | --- | --- | --- |
| `USER_REQUEST_INVALID` | 参数校验失败（含密码强度不足，消息指明规则） | 请求参数不合法 | 400 |
| `USER_OPERATION_FORBIDDEN` | 无功能权限 | 无操作权限 | 403 |
| `USER_NOT_FOUND` | 用户不存在或范围外 | 用户不存在 | 404 |
| `USER_DEPARTMENT_UNAVAILABLE` | 部门不存在 / 不可管理（404）或已停用（422） | 部门不可用 | 404 / 422 |
| `USER_ROLE_UNAVAILABLE` | 角色不存在 / 不可授予（404）或已停用（422） | 角色不可用 | 404 / 422 |
| `USER_USERNAME_DUPLICATE` | 用户名冲突 | 用户名已存在 | 409 |
| `USER_MOBILE_DUPLICATE` | 手机号冲突 | 手机号已存在 | 409 |
| `USER_VERSION_CONFLICT` | 编辑版本冲突 | 用户信息已被其他管理员修改 | 409 |
| `USER_SELF_DISABLE_FORBIDDEN` | 停用本人 | 不能停用自己 | 422 |
| `USER_LAST_SUPER_ADMIN_PROTECTED` | 停用唯一超级管理员 | 唯一超级管理员受保护 | 422 |
| `USER_SELF_ROLE_CHANGE_FORBIDDEN` | 修改本人角色 | 不能修改自己的角色 | 422 |
| `USER_DATABASE_OPERATION_FAILED` | 未映射的数据库错误 | 系统异常 | 500 |

> 错误码前缀 `USER_` 沿用部门模块 `DEPARTMENT_` 的命名约定（设计建议）；是否需要全局错误码注册表 **待确认**（项目当前为模块前缀模式）。各 API Spec 需要新错误码时，必须先在本表登记再引用。

## 13. 日志与审计

**必须记录审计的操作（已确认，PRD §11）**：新增、编辑、启用、停用、重置密码（删除能力本期不存在）。

| 记录项 | 要求 | 来源 |
| --- | --- | --- |
| 操作人 | `actor_id` | 已确认 |
| 目标用户 | `user_id` | 已确认 |
| 操作类型 | `action` | 已确认 |
| 操作时间 | `occurred_at` | 已确认 |
| 操作结果 | 成功 / 失败 | 已确认（PRD §11） |
| 变更前后快照 | `before_data` / `after_data` | 设计建议（对齐部门审计）；**不得包含密码凭据**（已确认，PRD §11） |

安全要求（已确认，PRD §11）：

- 密码不得以明文展示、存储或写入日志。
- 手机号展示是否脱敏由权限与合规策略决定（§5.6）。
- 后端必须再次验证权限，不能只依赖前端隐藏按钮。
- 成功提示与审计均不得包含初始密码 / 新密码（PRD §8.2）。

系统日志模块（`系统管理 / 系统日志`）尚未实现；本模块先以模块内审计表承载（设计建议），后续是否并入统一系统日志 **待确认**（§18 P2-4）。

## 15. 横切验收标准

每个 API 自己的验收标准写在该 API Spec 的第 11 节；本章只保留横切验收。

### 业务规则

- [ ] 列表 / 详情 / 组织树仅返回操作者数据范围内的数据；总数与人数只统计范围内。
- [ ] 「仅当前部门」不包含下级；「包含下级部门」只包含可见后代节点。
- [ ] 范围外目标一律 404，不暴露存在性。
- [ ] 停用保护：本人、唯一超级管理员在单个、批量、编辑三条路径上均不可停用。
- [ ] 本人角色不可通过编辑接口修改。
- [ ] 手机号 / 邮箱按敏感字段权限脱敏，完整值不先返回前端。

### 数据 / 数据库

- [ ] 写操作同事务写入用户行、部门引用、审计行（按 §7.3 的原子组）。
- [ ] 换部门时旧引用注销、新引用登记，无残留。
- [ ] 存在用户引用的部门无法被软删除（部门模块联动）。
- [ ] 审计记录包含操作人 / 目标 / 类型 / 时间 / 结果，且不含密码。
- [ ] 所有列表类查询条件包含租户 + 有效部门集合（范围进入查询条件，不做全量内存过滤）。

### 状态

- [ ] 初始状态默认 `active`，可显式创建 `disabled`。
- [ ] `active ⇄ disabled` 流转符合 §6 状态表；保护场景被拒绝。

### 权限

- [ ] 无对应权限码访问各接口返回 403。
- [ ] 全量范围操作者可管理租户内全部用户；范围操作者仅限可管理部门内用户。
- [ ] 集团根节点普通员工不因组织位置自动扩权。
- [ ] 编辑保存时目标已移出范围 → 拒绝并提示「该用户已不在你的管理范围内」。

### 事务

- [ ] 一致性组内任一步失败 → 无部分成功数据。
- [ ] 批量停用中单个用户失败不回滚其他成功项。

### 并发 / 幂等

- [ ] 两个管理员并发编辑同一用户：后提交者收到 409，数据不被覆盖。
- [ ] 并发创建相同用户名 / 手机号：仅一个成功。
- [ ] 并发停用超管场景下，最终不会出现零个正常状态超级管理员。
- [ ] 重复提交行为符合 §10.2。

### 异常

- [ ] 400 / 401 / 403 / 404 / 409 / 422 / 500 场景与 §11 一致。
- [ ] 可用性校验接口失败不被当作「可用」。

### 安全

- [ ] 密码不以明文存储、不回显、不进入响应 / 日志 / 审计。
- [ ] 创建 / 重置密码的成功提示不含密码。

- 不涉及移动端适配接口差异。
