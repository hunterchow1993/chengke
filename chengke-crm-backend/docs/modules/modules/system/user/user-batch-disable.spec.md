## 1. 接口概述

- **用途与调用场景**：管理员在工具栏勾选一个或多个用户后点击「批量停用」，二次确认对话框展示停用影响与选中人数，确认后执行（PRD §6.4、§7.4）。
- **功能权限**：`system:user:disable`；数据权限见总览 §8.2。
- **成功状态码**：200（部分失败仍返回 200 + 逐项结果，已确认默认允许部分成功，PRD §4.9）。
- **是否修改数据**：是。对每个成功项：修改用户行 `status`、新增审计行（总览 §7.3）。
- **引用章节清单**：
  - 总览 §4.2 全局约定、§5.2 越权保护、§5.3 保护账号规则与决策表、§5.4 授权边界（批量不绕过单条校验）
  - 总览 §6 状态流转、§9.3 批量部分成功语义
  - 总览 §10 并发、§11.2 错误码总表、§13 审计

---

## 2. 请求示例

```json
{
  "userIds": ["<uuid>", "<uuid>", "<uuid>"]
}
```

目标状态固定为 `disabled`（本接口只做批量停用；启用仅单个，见 [user-status.spec.md](./user-status.spec.md)）。

---

## 3. 请求参数（Controller 层契约）

| 参数 | 类型 | 来源 | 必填 | 默认值 | 校验规则 | 业务含义 |
| --- | --- | --- | --- | --- | --- | --- |
| `userIds` | UUID[] | Body | 是 | — | 非空；元素为 UUID；单次上限 100（设计建议，对齐角色管理批量成员上限；**待确认**，§12） | 待停用用户集合 |

---

## 4. 参数校验与业务校验

**参数校验**

- `userIds` 必填、非空、元素均为 UUID、数量 ≤100（上限待确认）。

**业务校验（对每个用户独立判断）**

- 用户存在且在操作者数据范围内（总览 §5.1 / §5.2）。
- 保护账号决策表（总览 §5.3）：本人、唯一超级管理员不可停用。
- 当前状态是否允许停用（已是 `disabled` 的处理 **待确认**，§12）。

---

## 5. 业务逻辑（Service 层）

```
请求 + JWT
→ 功能权限校验（disable，双层）
→ 参数校验（非空、上限）
→ 对每个用户独立执行：
    数据范围校验 → 读取最新状态 → 保护账号决策表校验
    → 通过：事务内更新 status + 写审计（action=disable）
    → 不通过：记录失败原因，继续下一个（单个失败不中断）
→ 至少一项成功 → 提交后授权版本 +1；失效相关缓存（总览 §9.1）
→ 返回 200 + 逐项结果与成功 / 失败统计
```

**逐项判定决策表（本接口特有）**

| 条件（对每个用户独立判断） | 允许 | 逐项结果 |
| --- | --- | --- |
| 在操作者范围内 且 `active` 且 非本人 且 非唯一超级管理员 | 是 | 成功，状态更新为 `disabled` |
| 不在操作者范围内 / 不存在 | 否 | 失败：用户不存在（404 语义，总览 §5.2） |
| 目标为操作者本人 | 否 | 失败：`USER_SELF_DISABLE_FORBIDDEN` |
| 目标为唯一超级管理员 | 否 | 失败：`USER_LAST_SUPER_ADMIN_PROTECTED` |
| 当前已是 `disabled` | **待确认** | 选中项包含已停用用户的处理规则未定义（PRD TOOL-04，§12）；设计建议：不执行停用，逐项结果标记失败并注明「已停用」 |

**部分成功语义（已确认，总览 §9.3）**：用户之间相互独立；单个用户的「状态 + 审计」仍必须原子；不允许通过批量绕过单条权限校验（总览 §5.4）。

## 6. 数据操作与 SQL（DAO 层）

| 操作 | 操作目的（服务的业务规则） | 数据来源 | 数据变化 |
| --- | --- | --- | --- |
| SELECT 每个目标用户最新状态与身份（逐项） | 逐项范围校验；保护规则基于提交时最新数据（总览 §10.1） | `userIds` + 租户 | 无 |
| SELECT 超级管理员正常状态用户计数 | 「唯一超级管理员」判定（总览 §5.3；计数实现依赖角色模块，总览 §18 P0-2） | 租户 | 无 |
| UPDATE `status`（每个成功项） | 状态流转（总览 §6） | `userIds` | 修改 `sys_user` 行 |
| INSERT 审计行（每个成功项） | 总览 §13 | 变更快照 + 操作者 | 新增 `user_audit_log` 行 |

数据访问模式与 [user-status.spec.md](./user-status.spec.md) §6 相同，按 `userIds` 逐项执行；不使用「全量或全无」的批量修改（部分成功语义）。

**`BatchDisableResultVO`**（结构为设计建议；「返回成功、失败数量与失败原因」为已确认要求，PRD §4.9 / §6.4 / §9.3）

| 字段 | 类型 | 一定存在 | 空值规则 | 业务含义 | 来源 |
| --- | --- | --- | --- | --- | --- |
| `total` | Integer | 是 | — | 提交的用户数 | 请求 |
| `successCount` | Integer | 是 | — | 停用成功数 | 计算 |
| `failedCount` | Integer | 是 | — | 失败数 | 计算 |
| `results` | Array | 是 | — | 逐项结果 | 计算 |
| `results[].userId` | UUID | 是 | — | 用户 ID | 请求 |
| `results[].success` | Boolean | 是 | — | 是否成功 | 计算 |
| `results[].errorCode` | String | 是 | 成功时为 `OK` | 失败错误码（总览 §11.2） | 计算 |
| `results[].message` | String | 是 | — | 失败原因摘要 | 计算 |

## 9. 成功 / 失败行为

**成功**：参数校验通过 → 逐项独立执行停用 → 返回 200 + 逐项结果与统计（即使部分失败仍为 200）。

**失败**：

| 场景 | 错误码（总览 §11.2） | HTTP | 业务是否终止 |
| --- | --- | --- | --- |
| `userIds` 为空 / 非 UUID / 超上限 | `USER_REQUEST_INVALID` | 400 | 是（整体拒绝） |
| 无 `system:user:disable` | `USER_OPERATION_FORBIDDEN` | 403 | 是（整体拒绝） |
| 逐项失败（范围外 / 本人 / 超管 / 已停用） | 逐项错误码记录在 `results` | 200 | 该项终止，其他项继续 |
| 单项数据库写失败 | `USER_DATABASE_OPERATION_FAILED` | 200（逐项记录）/ 整体 500 仅限请求级故障 | 该项回滚，其他项不受影响 |

---

## 10. 事务与并发要点

- **原子组**（总览 §7.3、§9.3）：每个成功用户自身的「状态 + 审计」必须原子；用户之间相互独立，单个失败不回滚其他成功项。
- **提交后**（总览 §9.1）：至少一项成功时授权版本 +1；失效相关缓存。
- **并发**（总览 §10.1）：
  - 批量停用与单条启用 / 停用并发：逐项以提交时最新状态判断，结果如实反映执行情况。
  - 「唯一超级管理员」判定并发：不得因批量 + 单个并发停用导致零个正常超管。

---

## 11. 验收标准（本 API）

- [ ] POST `/api/v1/system/users/batch-disable` 可正常调用，成功返回 200。
- [ ] 未选择用户（空数组）返回 400。
- [ ] 逐项独立校验：范围外、本人、唯一超级管理员逐项失败且不影响其他项。
- [ ] 部分成功时返回正确的 `successCount` / `failedCount` 与逐项原因。
- [ ] 每个成功项：状态更新 + 审计行成对出现；单个失败项无中间状态。
- [ ] 无权限时整体 403。
- [ ] 至少一项成功后授权版本 +1。
